# Project Presentation & Operational Design Guidelines

## 1. Editorial & Review Discipline (Surgical Edits Only)
- When asked to review, polish, or edit existing slides, copy, or text cards, **make surgical edits only**.
- Fix genuine bugs, typos, OCR errors, duplicate lines, or explicit requested removals.
- **Do NOT gratuitously rephrase or rewrite working sentences** that are already approved or adequate. Preserve the user's established phrasing unless a change is strictly necessary.

## 2. Presentation Slide Copy Standards
- **Telegraphic Syntax:** Keep slide bullets concise (bold anchor lead-in + 8 to 12 words maximum). Never write dense, multi-sentence paragraphs inside slide cards.
- **Plain-English Headlines (Zero Technical Jargon):** Main slide titles and major card headings must be benefit-led and immediately understandable to non-technical executive judges. Never use protocol acronyms, daemon names, or developer jargon (e.g., `Kamailio`, `SIP B2BUA`, `Media RTP`, `Redis`, `WORM`) in headlines.
- **Anti-Duplication Standard:** Backup slides must provide the underlying technical, operational, or legal defense answering tough judge attacks; never merely duplicate main deck summary bullets.
- **Large-Font Friendly:** All copy must be designed for 18pt–24pt typography with generous whitespace so it does not crowd illustrations or slide borders.
- **Hierarchy:** Clearly separate top trackers, main headlines, card titles, subtext, and bottom banners.

## 3. Executive Financial Presentation Rules
- **No Elementary Arithmetic:** Never write out basic arithmetic formulas (e.g., `+A − B = C`) on presentation slides. Present gross benefits, itemized deductions, and net EBITDA directly as distinct, professional financial metrics.
- **Itemized Audited Costs:** Explicitly list hard operational cost categories (OpEx, platform maintenance, FTEs, refund buffers) rather than hiding them or summarizing them into a single equation.

## 4. Operational Common-Sense Checks
- In operational and telecom field workflows, assess human incentives through friction reduction: if an action is already faster, simpler, and less error-prone for the user/retailer (e.g., 6 digits vs 11 digits), do not propose artificial cash subsidies or bonuses.

## 5. Executive Explainability & Metric Grounding
- **No Vanity Decimals or Unexplainable Milliseconds:** Never put arbitrary decimal figures (e.g., `21.4 ms`, `3.2 ms`) on slides. If the presenter cannot defend the exact empirical measurement in a 10-second jury exchange, use accepted industry standard thresholds (e.g., `<25 ms latency budget`) tied directly to human perception (e.g., `zero perceptible call lag`).
- **Core Mechanism Over Case Study Fluff:** Always dedicate slide space to the product's actual end-to-end mechanism (Activation ➔ Network Execution ➔ Expiry & Lawful Escrow) rather than filling cards with secondary external corporate news or regional precedent trivia.
- **Separate Slide Copy from Speaker Notes:** Keep on-slide copy ultra-compact (≤ 50 words per card); reserve deep citations, formulas, and extended explanations for speaker notes and companion markdown plans.

## 6. Dynamic Layout Invariant
- **Content-Driven Layouts:** Avoid repeating the same 3-card template across consecutive slides. Adapt layouts dynamically to the subject (e.g., 4-stage pipeline for webhooks, 2-world split-screen for network moats, phone UI mockups for USSD, clean tables for financial schedules).

## 7. Compact & Non-Bloated Notes Discipline
- **Zero Bloat Anywhere:** Never write dense, repetitive, multi-paragraph, or bloated notes in project documentation, markdown files, or Obsidian notes.
- **Telegraphic & High-Density:** Keep all explanations, problem-solution breakdowns, and architectural notes compact, crisp, telegraphic, and strictly value-additive. Cut all filler and rhetorical fluff.


## 8. Table Formatting Standard (Always Proper Markdown Tables)
- **Zero ASCII/Plaintext Box Tables:** Never format literal tables using ASCII box-drawing characters (e.g., +---, |, ┌───┐, ├────┤).
- **Always Proper Markdown Tables:** Always format tables as standard GitHub-flavored Markdown tables (| Col 1 | Col 2 | with | :--- | :--- | header dividers) so that Obsidian and markdown viewers render them natively, crisply, and responsively.
